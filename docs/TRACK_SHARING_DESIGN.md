# プロジェクトにおける軌跡共有の検討

作成日: 2026-08-30 / 更新: 2026-08-31
ステータス: ステップ0（バグ修正・整理導線）とステップ1（世代方式による5MB上限撤廃）実装済み。共有機能（ステップ2以降）は未着手

## 1. 目的

共有プロジェクトにおいて、メンバーが記録した軌跡（トラックログ）を他のメンバーと共有する機能を検討する。本書では現状の仕組みを整理し、共有形態の選択肢・制約（特にデータサイズ）・推奨案をまとめる。

## 2. 現状整理

### 2.1 軌跡データのライフサイクル

```
[記録中]
  BackgroundGeolocation.onLocation
    → checkAndStoreLocations()（精度100m超・タイムスタンプ逆転を除外）
    → MMKV(trackLogStorage) に 500点/チャンクで保存      ※完全ローカル。クラウドには一切上がらない

[保存時] useLocation.saveTrackLog()
    → 全チャンク結合 + cleanupLine（src/utils/Coords.ts:1001）
      ※この時点で既に間引き済み: 3点移動平均(smoothLine) + turf.simplify(Douglas-Peucker、
        許容誤差1e-6度≒0.1m)。生の全点はMMKV上の記録中データのみ。ただし0.1mはノイズ除去
        レベルでGPSの揺らぎより小さいため、長い軌跡では簡略化後も数千点残り得る
    → useRecord.addTrackRecord()
    → id:'track' の LINEレイヤ（permission:'PRIVATE'）の1レコードとして Redux dataSet へ
      ・coords: LocationType[]（各点に timestamp / altitude / speed / accuracy を保持）
      ・field: name(SERIAL) / time(DATETIME) / cmt(距離テキスト)

[アップロード時] useRepository.uploadDataToRepository('PublicAndPrivate')
    → getTargetLayers() は permission でのみフィルタするため track レイヤも対象
    → uploadDataHelper() で暗号化し projects/{id}/data へ（PRIVATE として）
```

- 軌跡サマリー（距離・時間・獲得標高・標高グラフ）は保存されず、`coords` から表示のたびに再計算される（`src/utils/trackStatistics.ts`）。**coords を間引くとサマリー精度も落ちる**点に注意。
- Web版は軌跡記録に非対応（閲覧は可能）。

### 2.2 現状の権限マトリクス（誰が誰の軌跡を見られるか）

| 閲覧者 \ データ | 自分の軌跡 | 他メンバーの軌跡 |
|---|---|---|
| OWNER / ADMIN | ○ | ○（PRIVATEデータを取得できる） |
| MEMBER | ○ | ×（Rules上、他人のPRIVATEは読めない） |

つまり **「管理者が全員の軌跡を収集・閲覧する」は現状で既に実現できている**。未実現なのは「一般メンバー同士の共有」。

### 2.3 track レイヤの permission が変更できない理由

track レイヤは `layersInitialState`（`src/modules/layers.ts`）で `permission:'PRIVATE'` に固定され、レイヤ一覧からレイヤ設定画面（LayerEdit）への遷移が
`src/components/organisms/LayersTable.tsx:90,193` / `LayersTable.web.tsx:109,211` の `item.id !== 'track'` ガードで塞がれているため、**UI上 permission を変更する手段がない**（事実上PRIVATE固定）。

### 2.4 先行実装: 現在地のリアルタイム共有

`src/hooks/useSyncLocation.ts` により、プロジェクト参加中は `projects/{id}/position/{uid}` に現在地をE2E暗号化してアップロードし、onSnapshot で他メンバーの位置を購読・地図表示している（`HomeMemberMarker`）。「記録中の軌跡のリアルタイム共有」を作る場合の直接の先行実装。

> ⚠️ 既存バグ（**ステップ0で修正済み**）: `useSyncLocation.ts` のスロットル判定が `dayjs().diff(lastUploadTime.current) / (60 * 1000) > 0` となっており、diff(ミリ秒)を60000で割っても正なら通るため意図の「60秒間隔」が効いておらず、位置更新のたびにアップロードされていた。`POSITION_UPLOAD_INTERVAL_MS`(60秒)の正しい間隔判定に修正済み（初回は即アップロード）。

### 2.5 暗号化との関係

データは `enc()/dec()`（`src/lib/firebase/firestore.ts`）でプロジェクト単位の共有鍵（DEK方式 or 旧グループ暗号）により透過的に暗号化される。**軌跡をどの permission・どのコレクションに置いても、鍵管理の追加実装は不要**。

## 3. 現状の問題点（共有機能と独立に対処価値あり）

### 3.1 5MB上限でアップロード全体が止まる

- アップロードは「userId × layerId × permission」1グループの全削除→全置換で、暗号化後サイズが 5MB（`MAX_SIZE_KB = 5000`、`firestore.ts:793`）を超えると拒否される。
- 拒否されると `useRepository.ts:625-628` で **即 return し、後続レイヤのアップロードもすべて中断**する。
- 暗号化前の圧縮はない（DEK方式は JSON.stringify をそのまま20000文字チャンクで暗号化）。軌跡1点は約200バイト → **5MB ≒ 1.5〜2万点**。1日の調査記録は数千点になるため、**軌跡を数回〜十数回分溜めて消さずにいると、軌跡以外も含むデータアップロード全体が失敗する**。
- track レイヤはレコード削除UIこそ通常レイヤと同じだが、「古い軌跡を整理する」導線・自動整理はない。

### 3.2 軌跡は蓄積が速いのに全置換方式

軌跡は追記型データ（過去の記録は変化しない）なのに、1点でも増えるとグループ全体を再暗号化・再アップロードする。通信量・書き込み回数の面でも非効率。

## 4. 共有形態の選択肢

### 案A: 保存済み軌跡の共有（track レイヤの PUBLIC 化）

保存した軌跡をメンバー全員が閲覧できるようにする。実装は「track レイヤの permission を PUBLIC に変更可能にする」だけで、以下がすべて既存のまま動く:

- アップロード/ダウンロード経路（PUBLIC は全メンバーが取得）
- Firestore Rules（PUBLIC の read は全メンバー許可済み）
- ユーザー別色分け（`colorStyle.colorType:'USER'`）
- データテーブルの `_user_` フィルタ、マージ・衝突解決
- 他人の軌跡タップ→TrackSummary 表示（coords があれば統計は再計算される）

変更点の中心:
1. permission 変更手段の提供（後述の未決事項: レイヤ設定を開放するか、専用トグルにするか）
2. `useRepository` の track レイヤ補完処理（`useRepository.ts:366-373, 920-925`）が permission を上書きしないかの確認
3. **サイズ対策（§5）が実質的な前提条件**（PUBLIC は全メンバーが全員分をダウンロードするため、蓄積問題が全員に波及する）

コスト: 小〜中（サイズ対策を含めると中）。

### 案B: 記録中軌跡のリアルタイム共有（ヤマレコ「いまココ」相当）

記録中の軌跡（直近の足取り）を他メンバーの地図にほぼリアルタイムで表示する。安全管理（メンバーの動きの把握、はぐれ・遭難対応）に有効。

- 実装は position 方式の拡張が自然: `projects/{id}/position/{uid}` の暗号化ペイロードに「直近軌跡（間引き済み座標列、例: 直近30分/最大100点）」を追加し、購読側で `HomeMemberMarker` に加えてポリライン描画。
- ドキュメント肥大を避けるため座標列は上限点数で切る。全履歴のリアルタイム共有はしない（保存後は案Aで共有）。
- 前提: §2.4 のスロットルバグ修正＋適切な間隔設計（電池・通信量とのトレードオフ。60〜120秒で十分）。
- バックグラウンド記録中もアップロードするには headless タスク側からの送信が必要になる可能性があり、ここが設計の山場（現状の position 送信はフォアグラウンドの `currentLocation` 変化駆動）。

コスト: 中〜大。通信量・電池への影響評価が必要。

### 案C: 管理者による収集閲覧（現状ですでに実現）

管理者が全員の軌跡を閲覧する用途は、PRIVATE のまま現状の仕組みで動いている。追加実装なし。「調査リーダーだけが全員の行動を把握したい」ならこれで足りる。

### 比較表

| | 案A: 保存済み共有 | 案B: リアルタイム | 案C: 管理者収集 |
|---|---|---|---|
| 見える人 | 全メンバー | 全メンバー | 管理者のみ |
| タイミング | アップロード後 | ほぼリアルタイム | アップロード後 |
| 主な用途 | 調査カバレッジ共有・重複回避 | 安全管理・当日の連携 | 進捗管理 |
| 実装コスト | 小〜中 | 中〜大 | ゼロ（済） |
| 通信量への影響 | 中（全員が全員分をDL） | 中（送信頻度次第） | 現状どおり |
| 主なリスク | 5MB上限の波及 | 電池・バックグラウンド送信 | — |

案AとBは排他ではなく補完関係（Bは「今」、Aは「記録」）。

## 5. サイズ問題への対策比較（案Aの前提、かつ現状問題§3.1の解消策）

| 対策 | 概要 | 長所 | 短所 |
|---|---|---|---|
| (1) 共有時の間引き | アップロード時に保存時（cleanupLine、許容誤差0.1m）より粗い許容誤差で追加簡略化。ローカルは保存時のデータを保持 | 実装最小。既存経路・構造を変えない。5MB到達を大幅に遅らせる | 他人から見た軌跡・サマリーの精度低下（timestamp間引きで速度/時間統計が粗くなる）。根本解決ではない |
| (2) 走行単位のドキュメント分割 | 軌跡専用サブコレクション（例: `projects/{id}/tracks/{uid}_{recordId}`）で1記録=1ドキュメント群 | 全点共有可能。追記型に合致し再アップロード不要。5MB上限は記録単位になり実質解消 | Firestore構造・Rules・同期/マージ・衝突検知の新規実装。既存レイヤ機構から外れる |
| (3) Storage退避 | 座標列を暗号化ファイルとして Storage へ（写真と同経路）。レコードには参照のみ | Firestore上限から解放。写真の既存パターン（url+key）を流用可 | ダウンロードが2段階になり一覧表示が重い。オフラインキャッシュ管理が必要 |
| (4) 保持ポリシー | 古い軌跡の整理UI（一括削除・アーカイブ・エクスポート済みの削除促し） | どの案とも併用可。ローカル肥大にも効く | 単独では上限問題を先送りするだけ |

**評価（2026-08-30決定）**: **(1) アップロード時の間引きは不採用**（ユーザー判断: アップロードで間引くのは望ましくない。クラウドにも保存時解像度のまま上げ、データの劣化を持ち込まない）。保存時には元から `cleanupLine`（平滑化＋DP 0.1m）のノイズ除去があり、それ以上の削減はしない。したがって5MB対策の軸は **(4) 保持ポリシー（古い軌跡の整理）を当面の運用**とし、蓄積・全点共有の要求に対する根本解決は **(2) 走行単位のドキュメント分割**で行う。(3) は (2) と競合する選択肢だが、軌跡は一覧性（開いたら全員分見える）が重要なので、Firestore内で完結する (2) を優先。

参考（サイズ感）: 軌跡1点約200B・暗号化後約260B。5MB ≒ 1.5〜2万点（userId×track×permission の合計）。cleanupLine 後も長い軌跡は数千点残るため、数記録〜十数記録で上限に達し得る。→ 最終的に(2)も過剰と判断し、書き込み設計の変更（§5.5 世代方式）で解決した。

## 5.5 世代方式による5MB上限の撤廃（**採用・2026-08-31実装済み**）

検討の変遷: (1)間引き→不採用、(2)走行単位分割→設計したが「1記録は最大でも1MB未満・5MBに達するのは蓄積のみ」という規模感に対して過剰と判断し不採用。最終的に、5MB上限の根本原因である**「全削除＋全書き込みを1つのwriteBatch（10MiBリクエスト上限）で原子コミットする」書き込み設計そのものを変更**する世代方式を採用した（全レイヤに効く・同期セマンティクス不変）。

### 前提知識

- 既存の900KBチャンク分割は「Firestoreの1MB/doc制限」対策であり、5MB上限は回避できない。5MB上限は1バッチ10MiB制限に対する保守的な値だった
- `src/utils/TrackLogSplitter.ts`（5000点分割・サイズ推定）は未使用のデッドコード（削除候補のまま）

### 方式（実装内容）

**書き込み（`uploadDataHelper`、firestore.ts）**
- 各アップロードの `encryptedAt`（全チャンク共通のTimestamp）を**世代ID**とし、全docに `chunkCount`（世代の総チャンク数）を付与
- **ハイブリッド**: 従来の5MB相当以下（`ATOMIC_MAX_KB=5000`）かつop数が収まるグループは、現行どおり削除＋書き込みを**1バッチで原子コミット**（既存挙動を完全維持）
- 大グループは**世代方式**: 新世代のチャンクを `MAX_BATCH_BYTES=8MB` / `MAX_BATCH_OPS=400` ごとの複数バッチで書き切ってから、開始時に存在した全doc（過去の残骸世代含む）をバッチ削除。書き込み途中の失敗は例外（不完全世代は読み側が無視）、削除フェーズの失敗は成功扱い（残骸は次回一掃）
- サイズ上限は `MAX_SIZE_KB=50000`（50MB）の暴走ガードのみに緩和。50MB ≒ 軌跡約19万点 ≒ cleanupLine後で数百日分に相当し実質無制限

**読み取り（世代選別 `selectCompleteGenerationDocs`、純関数）**
- (layerId×userId×permission)グループごとに「doc数==chunkCount かつ chunkIndex重複なし」を満たす**最新の完全世代**だけを採用
- `chunkCount` の無いレガシーdocは、**encryptedAtが不揃いでも1つの完全世代として束ねる**（旧実装はチャンクごとに別Timestampを書いていたため。分割するとレガシーデータ喪失）
- 適用箇所: `projectDataSetToDataSet`（全download系）/ `getMyDataUpdatedAt`（楽観ロック基準値）/ `getCloudDataSummary`（管理画面集計）/ `collectUnmarkedDekGroups`（DEK移行判定）
- 完全世代ゼロのグループは全docフォールバック（従来挙動）

**Rules**: `firestore.rules` の `verifyFields` 白リスト2箇所（通常経路57行・移行経路69行）に `"chunkCount"` を追加。**2026-08-31に本番(ecorismap)へデプロイ済み**（Rules先行が必要な変更のため。旧クライアントには影響なし）

**防御的変更**: `deleteData` / `deleteAllData` / `updateLayerDataPermission` も400件ごとのバッチ分割に変更（doc数増への備え）

### 安全性の考え方

- 書き込み中断 → 不完全な新世代は読み側が無視し、旧世代が生きたまま＝原子コミットと同等
- 削除中断 → 両世代残存だが読み側は最新完全世代を採用。残骸は次回アップロードで一掃
- 2端末同時アップロード → 後勝ち（従来と同じ）。世代ID衝突時はdoc数不一致で不完全判定→旧世代フォールバックの安全側
- 旧バージョンクライアントは世代選別を持たないが、削除フェーズ成功後は1世代のみなので通常は影響なし

### テスト
- 単体: `src/lib/firebase/__tests__/firestore.generation.test.ts`（世代選別8件・アップロード5件・読み側4件）。既存の1バッチ原子性テスト（selfMigration.test.ts）はハイブリッドによりそのまま通る
- Rules: `firestore_rules.test.ts` にchunkCount付きcreate成功＋白リスト回帰を追加（yarn testrules 120件パス）

## 7. 未決事項

1. **permission 変更のUI**: track レイヤのレイヤ設定を全面開放するか（フィールド編集等まで触れてしまう）、「軌跡を共有する」専用トグル（プロジェクト設定 or レイヤ一覧上）にするか。→ 誤操作リスクの少ない専用トグルを推奨
2. **共有の単位**: レイヤ一括（全軌跡を共有）か、記録単位で選択共有か。記録単位が必要になったら走行単位分割（不採用とした設計案）を再検討
3. ~~**間引き**~~: **不採用に決定**（2026-08-30）。保存時の cleanupLine（ノイズ除去、0.1m）以上の削減は行わず、クラウドにも保存時解像度で上げる。5MB対策は世代方式（§5.5、実装済み）で解決
4. **既存プロジェクトへの影響**: PUBLIC 化した track の permission はサーバ側 doc の permission フィールド更新（`updateLayerDataPermission`、管理者のみ）が必要になるケースの整理
5. **リアルタイム共有の仕様**: 更新間隔、直近何分/何点まで載せるか、プロジェクト退出・記録停止時のクリア
6. **プライバシー**: 軌跡は行動履歴そのもの。共有ON/OFFを本人が制御できること（管理者が強制しない）を原則とするか
