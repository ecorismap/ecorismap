# ログインとプロジェクト管理の監査（2026-11）

2026-11-23 実施。ログインとプロジェクト管理で次のことが起きる経路を探した。別のアカウントに前の人の状態が引き継がれる。プロジェクトのデータや設定が消える、または別のプロジェクトへ混ざる。開けない・消せないプロジェクトが残る。権限の表示と実際がずれる。失敗したのに成功と表示される。

- **範囲**: Google 連携（Drive 個人プロジェクト）と組織アカウント（Firebase メール認証）のログイン・ログアウト・アカウント切替、メール確認、パスワード再設定、プロジェクトの作成・一覧・開く・閉じる・切替・削除、メンバー管理（招待・権限変更・保留メンバー・削除）、アカウント削除。主なファイルは `useAccount.ts`、`useProject.ts`、`useProjects.ts`、`useProjectEdit.ts`、`useGoogleDriveProjects.ts`、`useGoogleAccount.ts`、`useRepository.ts`（プロジェクトを開く・同期の部分）、`lib/firebase/sign-in*.ts`・`firestore.ts`（プロジェクト部分）、`lib/googledrive/*`、`containers/Account.tsx`・`AccountSettings.tsx`・`Projects.tsx`・`ProjectEdit.tsx`・`GoogleDriveProjects.tsx`。暗号鍵そのものの扱いは暗号監査（`CRYPTO_AUDIT_2026-11.md`）で済んでいるので、ここではログイン状態やプロジェクト操作との関係だけを見た。
- **方法**: 観点（ログイン、プロジェクト、メンバー、Drive、画面表示）ごとに候補を出し、重複をまとめた。各候補を3人が別々に検証し、実在するか、重大度、分類、手順に訂正があるかを投票した。重大度・分類・手順は3票の多数に従い、訂正は本文に反映した。既存の監査報告書（インポート/エクスポート・同期・軌跡・暗号・写真・地図タイル）、メモリ、git log で既知・修正済みのものは再報告していない。
- **結果**: 確認 28件（**high 3、medium 8、low 17**）。うち安全に直せる 20件、判断が要る 8件。反証 1件。
- コードは変更していない。手順はコードとライブラリのソースを読んで成り立つと確認したもので、実機では確かめていない。
- **分類**: **安全に直せる**＝挙動の方針を変えずに直せる。**判断が要る**＝挙動や仕様を変えるので、どちらにするか決める必要がある。

### A-H1. 設定モードのまま別の（または同じ）プロジェクトを通常の「開く」で開くと設定モードが残り、「保存」で管理者自身の PRIVATE/PUBLIC の記録がテンプレートとして全メンバーに配られる【安全に直せる】

- **対象**: Web だけ。設定モードの入口（「設定」ボタン）は `ProjectEditButtons.tsx:49` で `Platform.OS === 'web'` のときしか出ない。
- **手順**
  1. 管理者がプロジェクトAの「設定」を押して設定モードに入る（`startProjectSetting` で `isSettingProject=true`）。
  2. ホームのアカウントボタン →「プロジェクト」（`Home.tsx:2398` の `gotoProjects` は設定モードでも止めない。`Projects.tsx:51` が止めるのは新規作成だけ）→ AかB（自分が管理者）→「開く」を押す。「開く」が無効になるのは `isEdited` のときだけ。
  3. 開き直しの確認に OK すると、`pressOpenProject(false)` が通常モードで設定・COMMON・PUBLIC・自分の PRIVATE・テンプレートを取り込む。`downloadProjectSettings` が書き戻す設定（`useRepository.ts:1389-1396` の ProjectSettingsType）に `isSettingProject` は入っていない。`openProject()`（`useProjectEdit.ts:72-82`）も role・projectId・projectName しか書かない。`isSettingProject` を false に戻すのは `clearProject`（`useProject.ts:96-106`）と `useEcorismapFile` だけで、この経路はどちらも通らない。
  4. ホームは設定モードとして表示され、ボタンは「保存」「破棄」だけになる（`HomeProjectButtons.tsx:37-54`）。
  5. 「保存」を押す。開いた直後なので `isProjectSettingCurrent` は一致し、確認は出ない。`saveProjectSetting` → `uploadDataToRepository(project,'Template')` に進む。`mergeTemplateRecords`（`useRepository.ts:795-829`）は `userId===user.uid` の記録を `userId:'template'`・表示名「管理者」に書き換えて送る。除外されるのは軌跡レイヤだけ（`useRepository.ts:877`、T-M9）。
- **根拠**: `useProjectEdit.ts:68-82`、`containers/ProjectEdit.tsx:158-257`、`useProject.ts:96-106, 121-147`、`useRepository.ts:795-829, 877, 1569-1625`、`HomeProjectButtons.tsx:37-54`、`HomeAccountButton.tsx:107-115`、`Projects.tsx:49-63`
- **影響**: 非公開のつもりの PRIVATE を含む管理者の記録が、テンプレートとして全メンバーの地図に配られる。以後「保存」するたびに送り直される。本来の設定モードは `downloadDataForSetting` で COMMON とテンプレートしか取らないので起きない。設定モードが残っている間は `isRunningProject=false` なので、通常のアップロードも軌跡のアップロードも行われない。MEMBER のプロジェクトBを開いた場合は設定モードの画面が出たままになり、「保存」は Rules で拒否されてエラーになる。
- **修正案**: `useProjectEdit.openProject` の `editSettingsAction` に `isSettingProject: false` を加える。`pressSettingProject` は開いた後に `startProjectSetting` で true に戻すので、正規の入口は変わらない。
- 任意の追加策（判断が要る）: 設定モード中は一覧や ProjectEdit の「開く」を止めるか、「設定を破棄して開きますか」と確認する。

### A-H2. プロジェクトAを開いたままBを開いて途中で失敗すると、Aの名前のまま手元が空（またはBの構成）になり、そのままアップロードするとクラウドのAの自分のデータが空で置き換わる【安全に直せる】

- **原因**: 開く処理が途中で失敗しても元に戻さない。
  - `pressOpenProject`（`containers/ProjectEdit.tsx:182`）が同期の基準値を捨てるのは開く先 `targetProject.id` だけ。今開いているA（`settings.projectId`）の `dataSync` は残る。切替は `clearProject`（基準値を捨てる、`useProject.ts:89-95`）を通らない。
  - `downloadProjectSettings`（`useRepository.ts:1586`）は取得の前に `setDataSetAction([])` で手元を空にする。設定の取得が成功すると `1618-1622` で layers・tileMaps・settings（updatedAt を含む）をBのものに置き換える。
  - その後に設定・辞書・スタイル・COMMON・PUBLIC/PRIVATE・テンプレートの取得やマージで throw すると、catch（`ProjectEdit.tsx:237-241`）はアラートを出して false を返すだけ。`openProject()` は成功時（228行）しか呼ばれないので、projectId・projectName・role・isSettingProject はAのまま残る。
- **手順と症状**
  1. Aを開いて一度アップロードしておく（Aの基準値が残る）。
  2. 一覧 → B →「開く」→ 開き直しの確認に OK。開いている途中で回線が切れる・圏外に出る・取得エラーが返る。最初からオフラインだと `loadE3kitGroup(B)` が手元を空にする前に失敗するので起きない。
  3. **設定の取得で失敗した場合**: 手元は「Aのレイヤ＋空の dataSet」、updatedAt もAのまま。ホームはAとして表示される。アップロードを押すと、`isSettingsUpdatedAtCurrent` が true、Aの基準値はクラウドと一致するので内容を比べずに continue する（`useRepository.ts:908-925`）。手元が空なので vanished の確認にも当たらない。`getTargetRecordSet` の空集合でクラウドのAの自分の PUBLIC/PRIVATE が全置換される。
  4. **設定の取得後に失敗した場合**: レイヤ・地図・updatedAt はB、名前はAになる。`findSettingsMismatchedLayers`（`ownDataSync.ts:16`）が止めるのは権限が食い違うレイヤだけで、ID が共通の `track` は素通しなので、Aのクラウドの軌跡がBの取得途中の内容（多くは空）で置き換わる。
  5. **設定モード中だった場合**: 設定モードのまま、Bの updatedAt とレイヤ構成を持ったAになる。「設定を保存」（`Home.tsx:2351-2376`）で `isProjectSettingCurrent` が false になり「別の端末で保存されています。上書きしますか」が出る。上書きを選ぶと、Aのクラウド設定（レイヤ構成・地図・共有範囲）がBの構成で上書きされる。表示はAのままなので取り違えに気づけない。
- **根拠**: `containers/ProjectEdit.tsx:179-245`、`useRepository.ts:908-925, 1569-1626`、`useProject.ts:89-95, 115-123`、`ownDataSync.ts:16`、`Home.tsx:2351-2376`、`docs/SYNC_AUDIT_2026-11.md:21, 109-114`
- **影響**: Aでアップロード済みの自分のデータ（特に軌跡）が、確認も表示もなくクラウドから消える。共有レイヤなら他のメンバーの画面からも消える。手元のAの未アップロード分は projectOpen の自動バックアップ（ネイティブのみ）にしか残らない。同期監査 S1 の修正案にあった「失敗したら元に戻す」は入っておらず、修正状況は「開く・閉じるときの基準値破棄」までなので、切替の失敗経路が残っている。
- **重大度について**: 設定モードでの上書き（手順5）は利用者が確認に同意する必要があり、単独なら medium 相当。根が同じなので1件にまとめ、データが黙って消える手順3を基準に high とした。
- **修正案**
  - pressOpenProject の開始時に、開く先に加えて今開いているプロジェクト（`settings.projectId`）の基準値も `clearDataSyncProjectAction` で捨てる。次のアップロードは必ず内容を比べる（バックアップ復元と同じ扱い）。手順3はこれで防げる。成功して開いた場合、Aの基準値は次にAを開くとき捨てられるので通常の挙動は変わらない。
  - 開始時に settings・layers・tileMaps・dataSet（と dataSync）の写しを取り、catch で書き戻す（projectOpen の自動バックアップと同じ内容を戻してもよい）。手順4・5はこれで防げる。`discardStaleTileSources` で消したタイルや辞書・スタイルの取得結果は戻らないので、失敗時に `clearProject` で「閉じた状態」に落とす案と比べて決める（その選択は判断が要る）。
  - 「開く前に NetInfo で接続を確かめる」は、途中で切れる場合とネイティブの `getDoc` がキャッシュから返る場合を防げないので、補助にとどまる。

### A-H3. 保留メンバーの再チェックで一般メンバーの「開く」が無効になり、プロジェクトを開けなくなる【安全に直せる】

- **手順**
  1. 管理者が未登録アドレスXを保留（NO_ACCOUNT、uid=null）のまま保存する。
  2. Xがサインアップしてメール確認を済ませる。
  3. 一般メンバーM（管理者ではない）がプロジェクト一覧からそのプロジェクトを選び、ProjectEdit を開く（一覧からプロジェクトを開く入口は ProjectEdit しかない。`Projects.tsx:67-76`）。
  4. 再チェックの effect（`useProjectEdit.ts:116-145`）は役割を見ずに `getUidsByEmails` を呼ぶ。サーバー側（`functions/src/ecorismap-func.ts:107-137`）は認証済み・メール確認済み・App Check しか見ないので、一般メンバーにも uid が返る。effect はXを HOLD（オレンジ）にして `setIsEdited(true)` にする。
  5. Mの画面に保存ボタンは出ない（`pages/ProjectEdit.tsx:63-71` は `isOwnerAdmin || isNew`）。一方「開く」は `disabled={isEdited}` で無効になる（`pages/ProjectEdit.tsx:169-178`、`ProjectEditButtons.tsx:38-46`）。戻ろうとすると「変更を破棄しますか」が出る（`containers/ProjectEdit.tsx:424-430`）。
- **根拠**: `useProjectEdit.ts:48, 116-145`、`pages/ProjectEdit.tsx:63-71, 169-178`、`ProjectEditButtons.tsx:38-46`、`containers/ProjectEdit.tsx:424-430`、`Projects.tsx:67-76`
- **影響**: 一般メンバーは、オーナーか管理者が保存し直すまで、どの端末からもそのプロジェクトを開けない。画面を開くたびに同じになる。保留中の人が登録するたびに起きる。オーナー・管理者も、画面を開くたびに保存を求められ、その間は「開く」などが無効になる。
- **修正案**: 再チェックで HOLD バッジの表示は全員に反映し、`setIsEdited(true)` は管理者・オーナーのときだけ呼ぶ。`isOwnerAdmin` は `targetProject` から導いた値なので、`initialProject` と `user.uid` から判定するか、描画時に「開く」の disabled を `isEdited && isOwnerAdmin` にするほうが確実。
- 管理者・オーナーの「開く」も無効にしたくないなら、「保存で有効化できる」ことを `isEdited` とは別のフラグで持つ（挙動が変わるので判断が要る）。
- 補足: effect 内の `getUidsByEmails` は失敗すると throw する（`firestore.ts:298-300`）が try/catch が無いので、照会が失敗すると未処理の Promise 拒否になる。
