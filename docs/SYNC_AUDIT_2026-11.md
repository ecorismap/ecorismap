# 共同編集の同期と競合解決の監査（2026-11）

2026-11-22 実施。複数人・複数端末で編集したときに、データが黙って消える、古い値に戻る、他人の変更を上書きする、重複する、別ユーザーのデータに化ける経路を探した。

- 方法: 6観点（マージ、アップロード、削除、権限、設定、端末とライフサイクル）で並行して探し、47件を見つけた。重複をまとめて32件にし、1件ずつ反証を試みた。可能なものは Jest の一時テストで再現した（一時ファイルは削除済み）。最後に見落としの確認と順位付けを行った。
- 結果: 確認31件（high 5、medium 13、low 13）、反証1件、見落としの確認で2件追加。
- 「再現」は Jest で手順を再現できたもの。それ以外はコードを読んで手順が成り立つと確認したもので、Firestore エミュレータを通した確認ではない。
- コードは変更していない。
- 分類: **安全に直せる**＝仕様を変えずに直せる。**判断が要る**＝挙動や権限設計、データ形式の判断が要る。

## 優先して直すもの（high）

### S1. 開き直しや復号に失敗してローカルが空なのに、同期済みと判定されてクラウドが消える【安全に直せる・再現】
- **手順**
  1. プロジェクトを開く処理で、ローカルを消した（`setDataSetAction([])`）あとに失敗する。失敗する箇所は、設定・辞書・スタイル・COMMON・PUBLIC・PRIVATE・テンプレートの取得や、マージのどれか。自分のデータが復号できない（`dec` が undefined）場合も同じ。
  2. そのまま記録してアップロードする。
- **結果**: `dataSync` の基準値が残っているため、衝突確認なしにクラウドの自分のデータが全件置き換わる。表示は成功のみ。共有レイヤなら他のメンバーの画面からも消える。自動バックアップ（projectOpen）には残るが、利用者は気づけない。
- **箇所**: `useRepository.ts:525, 549-557`、`ProjectEdit.tsx:140-205`、`firestore.ts:795-812`、`modules/dataSync.ts:41`
- **修正案**: ローカルの dataSet を捨てる・置き換えるすべての経路（開く、clearProject、バックアップからの復元、ファイルを開く）で `clearDataSyncProjectAction(projectId)` を呼び、次のアップロードで必ず内容を比較させる。開く処理に失敗したら元の状態に戻す。自分のデータが復号できなければ isOK:false にしてアップロードを止める。

### S2. COMMON のアップロードが先頭の DataType だけを送るため、別の管理者の追加・編集が消える【安全に直せる・再現】
- **手順**
  1. 管理者1が COMMON レイヤに記録 X を作って保存する。
  2. 管理者2が X を編集し（userId が違うので、自分のバケットに X' として移る）、Y を追加して設定を保存する。
- **結果**: `getTargetRecordSet` が `dataSet.find(layerId)` で最初に見つかった管理者1のバケットだけを送る。クラウドには X の墓標だけが残り、X' と Y は消える。表示は成功。
- **箇所**: `utils/Data.ts:462-484`、`useRepository.ts:599-603`
- **修正案**: COMMON は `filter` で全バケットを集め、id ごとに統合してから送る（削除されていないものを優先し、updatedAt が新しい方を採る）。

### S3. PUBLIC/PRIVATE のレイヤを COMMON に変えて保存すると、全メンバーのデータが消える【判断が要る（一部は安全に直せる）】
- **手順**
  1. メンバーが PUBLIC レイヤ L に記録をアップロードしておく。
  2. 管理者が設定モードで L の共有範囲を COMMON に変えて保存する。
- **結果**: `deleteCommonAndTemplateData` が `deleteData(projectId, L)` を permission も userId も指定せずに呼ぶ。layerId だけの条件で、全メンバーの PUBLIC/PRIVATE の doc が消える。そのあとの `updateLayerDataPermission` は対象が0件になる。確認は汎用の「保存しますか」だけ。
- **箇所**: `useProject.ts:101-113`、`useRepository.ts:452-468, 762-773`、`firestore.ts:571-597`、`useLayerEdit.ts:97-100`
- **修正案（安全）**: deleteData の対象を permission=COMMON に限る。権限の付け替えを削除より先に行う。
- **判断が要る点**: COMMON に変えたとき、メンバーのデータを COMMON に取り込むか、件数を示して確認するか。

### S4. 作図などで形を変えても updatedAt が更新されず、「最新優先」や衝突の検知で古い版が勝つ【安全に直せる・再現】
- **手順**: 同じアカウントの端末 A・B を使う。B が先にアップロードする。A が作図で線の形を変えて（updatedAt は元のまま）アップロードし、「マージ」を選ぶ。
- **結果**: updatedAt が同じなので、クラウドの版が勝つ。A の形の変更は消え、ローカルもクラウドの版で上書きされる。ダウンロード時の一括「最新優先」でも同じことが起きる。
- **対象の操作**: 作図での変形、色・太さの変更、行動記号の集約、子記号の再投影、選択肢名の一括書き換え、マップメモの Undo/Redo。
- **箇所**: `useRecord.ts:300-320`、`useDrawTool.ts:1034, 1084, 1156, 1191, 1281`、`useMapMemo.ts:1046, 1094`、`Home.tsx:1066-1080`
- **修正案**: レコードを書き換える経路で必ず updatedAt を更新する（reducer でまとめて付けてもよい）。値が同じときはローカルを優先するか、競合として扱う。

### S5. 並べ替えやマップメモの Undo/Redo で、墓標と `_group` の子レコードが消える【安全に直せる・再現】
- **手順**: 飛翔図の線に行動記号（`_group`）が付いた状態で、データ一覧をドラッグして並べ替える。墓標を含むメモレイヤで Undo/Redo する場合も同じ。
- **結果**
  - 並べ替えでは、行動記号がストアから消え、次のアップロードでクラウドからも消える。
  - どちらの操作でも墓標が消えるので、別の端末から古い版がアップロードされると、削除したものが確認なしに戻る。
- **箇所**: `useData.ts:86-94, 188-208`、`modules/selectors.ts:70-77`、`useMapMemo.ts:147, 233-240, 1045-1050, 1093-1098`
- **修正案**: 全体を置き換えるのをやめる。表示しているレコードの順序だけを入れ替え、墓標と子レコードはそのまま残す。

## 修正状況（2026-11-22、ブランチ fix/sync-high-severity）

high の5件を直した。修正のあと2回レビューを行い、確認された指摘も直した。

- **S1**
  - プロジェクトを開くときと閉じるとき（`clearProject`）に、同期の基準値を捨てる。
  - 衝突を確かめる取得（`getMyDataUpdatedAt`、内容比較用のダウンロード）が失敗したら、アップロード全体を中止する。メッセージは `cannotVerifyCloudData`。
  - クラウドに自分のデータがあるのに復号できないレイヤは、そのレイヤだけ送らずに残す。他のレイヤは送り、警告 `skippedUnreadableLayers` を出す。
  - あわせて M7 も解消した。
- **S2**
  - `mergeCommonRecords` で、COMMON の全バケットを id ごとにまとめてから送る。優先順は、削除されていないもの、updatedAt が新しいもの、自分のバケットの順。
- **S3**
  - 保存の最初に COMMON を消すのをやめた。
  - 権限を付け替えたあと、毎回 `downloadCommonData` で COMMON を取得する。そのうえで `buildCommonAbsorption` で取り込み、自分の名義にまとめて送る。
  - 書き込みに成功したあとで、内容を持っている人の分だけ、他人名義の doc を `deleteOtherUsersData` で片付ける。COMMON にしたレイヤのテンプレートも消し、手元のバケットも1つにそろえる。
  - テンプレート由来で id が重なる記録は、版（更新日時と内容）で比べる。版が違えば新しい id を振って両方残す。同じ版なら1つにする（保存をやり直しても複製しない）。
  - 復号できなかった人の doc は消さない。
  - 置き換えインポートで消える記録のうちアップロード済みのものは、墓標として残す（`replaceRecordsKeepingTombstonesAction`）。
  - PUBLIC/PRIVATE のテンプレートは、送る直前に削除する。
- **S4**
  - updateRecord、子記号の再投影、削除した記号の Undo、選択肢名の一括書き換えで updatedAt を進める。
  - 衝突時のマージでは手元の版を先に渡し、同じ時刻なら手元を採る。
  - `latest` では updatedAt が無いものを0とみなす（M6 の一部）。
- **S5**
  - 並べ替えでは、一覧に出ない墓標と子レコードを残す。
  - マップメモの Undo/Redo は `mergeMemoHistoryResult` で確定する。消えた線は墓標にし、戻した・変えた線は updatedAt を進めてアップロード済みの印を引き継ぐ。既存の墓標は残す。

### 残る制限
- 開いた直後の最初のアップロードは、必ず内容を比べる。他人の版を選んだ記録が手元から外れていると、別端末で変更していなくても衝突の確認が出ることがある（データは失われない）。
- COMMON にするとき、テンプレート由来の記録に新しい id を振る。その記録を別レイヤの REFERENCE（主キーが _id）が参照していても、参照値は付け替えない。子は元の id の版の下に表示される（子の記録自体は残る）。
- 管理者が並行して設定を保存したときの競合（M2）は未対応。
- Firestore エミュレータでの通し確認と、実機での確認はしていない。

## medium の修正状況（2026-11-22、ブランチ fix/sync-medium）

- **M5**: 一括解決（`handleBulkSelect`）の指定は、その取得の残りにだけ効かせる。`createMergedDataSet` の開始時と終了時に解除する。「自分優先」で自分の候補が無いときは最新を採り、updatedAt が無い候補は最も古いとみなす（M6 の一括側も解消）。
- **M3**: `updateStoragePhoto` は Storage の写真をその場では消さない。データの書き込みに成功したあとで、マージ後のデータのどの記録からも参照されていない写真だけを消す。
- **M4**: 写真の保存先を `photoDownloadPath.ts` で決める。基準は写真をアップロードした人で、URL の Storage パスから読む（読めないときは記録の持ち主）。自分が撮った写真は従来どおり自分のフォルダに写真名で、他人が撮った写真はその人のフォルダに「写真id_写真名」で置く。自動の取得にも、データ編集画面の「写真をダウンロード」にも使う。
- **M2**: 設定の保存の前に `isSettingsUpdatedAtCurrent` で、開いたあとに別の端末が設定を保存していないかを確かめる。保存されていた場合と、確かめられない場合は、「上書きして保存」か「キャンセル」かを尋ねる。

### 残る制限
- M4: 更新前の端末で、他人の写真を「自分のフォルダ/写真名」に保存していた場合は、新しい保存先へ一度ダウンロードし直す。古いファイルは自動では消さない。そのファイルが自分の写真とすり替わっていた可能性があり、消すと自分の原画を失うおそれがあるため。
- M2: 確かめてから書き込むまでの間（数秒）の競合は防げない（トランザクションは未対応）。

## 残りの medium・low の修正状況（2026-11-22、ブランチ fix/sync-remaining）

4つのまとまりに分けて順に直した。修正後のレビューで確認された2件（L2・L14）も直した。Rules は変更していない。

- **M9**: `projectDataSetToDataSet` の組のキーに permission を含める。エクスポートで同じ管理者の TEMPLATE と PUBLIC が混ざらなくなる。
- **M11**
  - 辞書を版付きのパス（`DICTIONARY/{layerId}/dictionary_{ulid}.sqlite`）に書き、設定に `dictionaryVersion` を持たせる。設定の書き込みに成功してから、旧形式のパスへ写し（更新前のアプリ向け）、古い版を消す。
  - 手元に辞書表の無いレイヤは上げない。
  - 辞書を取得できなかったときは利用者に知らせる。
- **M14**: マップメモ・作図の子（`_group`）の削除・表示切替・書き出しで、子をレイヤの全レコードから探す。マップメモ以外の作図レイヤでも、子を一緒に扱うようになった。
- **L2**
  - 取り直したレイヤで、取得結果に無い他人のバケットを手元から消す。自分・未ログイン時のバケットとテンプレートは消さない。
  - 復号できなかった人の写しは残し、件数を知らせる。
  - 管理者が PRIVATE を取得しなかったときは、他人の分を消さない（`pruneOthers:false`）。
- **L3**: テンプレートの記録がすべて利用者の版に置き換わったら、空のテンプレートにそろえる。取得結果に無いテンプレートは消す。
- **L5**: `uploadDataHelper` に期待値（判定に使ったクラウドの版）を渡し、書く直前に違えば書かずに中止する（「別の端末で更新されたので、もう一度アップロードしてください」）。
- **L7**: 新しい世代の encryptedAt を、既存の最大値より必ず大きくする。
- **L8・L9**: 自己DEK移行と共有データの再暗号化は、書き戻す直前に版が読んだ時点と同じか確かめる。違えば書かない。
- **L10**: クラウドデータ管理のレイヤ削除を、トランザクションで読みと書きをまとめて行う。
- **L12**: 設定の保存で、旧設定にあって新設定に無いレイヤ（track・LAYERGROUP を除く）の doc と写真を片付ける。
- **L13**: アップロードが途中のレイヤで止まっても、先に成功したレイヤの基準値を保存する。
- **L14**: Web 版で、アップロードしていない自分の変更があるときだけ、タブを閉じる前にブラウザ標準の確認を出す。他のメンバーの記録は判定に含めない。

### 残る制限
- L5・L8・L9・M2 は「書く直前に確かめる」方式で、確かめてから書き込むまでのごく短い間の競合は防げない。
- L2: 復号できなかった人の写しは、古い内容のまま表示が残る。
- L10 のトランザクションは、ネイティブ（React Native Firebase）では型チェックしかしておらず、実機では動かしていない。M11 のネイティブでの辞書アップロードも確かめていない。
- L14 は、ブラウザ標準の文言で確認が出る。安全側に倒しているので、確認がやや多めに出ることがある。
- 実機と Web の画面での確認はしていない。

## 判断待ちの方針（2026-11-22 決定）

| 番号 | 方針 |
|---|---|
| M8 | 他人・テンプレートの記録を削除できるのは管理者だけ。管理者の削除は自分の名義に墓標を持たせてアップロードし、他のメンバーの手元からも消す。一般メンバーは削除できない |
| M10 | クラウドの設定と権限が食い違うレイヤはアップロードを止め、設定を取り込み直すよう案内する。他のレイヤはそのまま上げる |
| M12 | 仕組みは変えない。共有プロジェクトで属性の名前や型を変えるときに「メンバーのデータは移行されない」と警告する |
| M13 | 軌跡の記録中にプロジェクトの切替・閉じる・ログアウトをするときは確認を出し、記録を止めて元のプロジェクトへ保存してから進める |
| L1 | 他人の記録を編集できるのは管理者だけ（M8と揃える）。管理者の編集は引き継ぎ元を記録し、競合を出し続けないようにする |
| L4 | ホームの「データ取得」に自分のクラウドデータも含め、手元と食い違う分は既存の競合解決で合わせる |
| L6 | 現状維持（レコード単位の最新勝ち） |
| L11 | 前回同期したのにクラウドから消えている記録は、再アップロードの前に確認する |

### 決定した方針の実装後レビューの対応（2026-11-22、ブランチ fix/sync-decided）

- **M8（編集中の削除）**: データ編集で編集中のまま「削除」したとき、先に保存しない。保存すると他人の記録は管理者の名義へ引き継がれ、続く削除が元の名義に向いて空振りし、編集版が削除されずに残っていた。削除は保存済みの版を墓標にし、編集で足した写真・外した写真の両方を手元から消す。
- **L1（テンプレートの削除の墓標）**: 管理者がテンプレートを消した墓標（引き継ぎ元が `template`）は、テンプレートを自分の記録にしたメンバーの版と競合させず、横に並べて残す（`separateTemplateDeletionTombstones`）。墓標はテンプレートを打ち消し続け、メンバーの版も残る。取得のたびに競合が出ることはない。
- **M8（他人の PRIVATE を取得しない管理者の取得）**: 取り直した範囲の外（`pruneOthers:false`）でも、マージ結果に現れなかった他人のバケットから、引き継ぎで打ち消された記録を外す。
- **L1（地図上のポイントのドラッグ・現在地で位置を更新）**: 他のメンバー・テンプレートの記録を動かせないときは、確認より前に元の位置へ戻し、理由を出す。
- **M13（記録中の切替・閉じる・ログアウト）**: 軌跡の確認 → 操作そのものの確認 → 停止・保存 の順にした（`leaveWithTrackingGuard`）。どちらかの確認でキャンセルしたら、記録を続けたまま何もしない。通常利用中のプロジェクトでは、保存した軌跡（軌跡レイヤだけ）をアップロードしてから進み、アップロードできなければ操作を中止する。設定の編集中は軌跡をアップロードせず、閉じると破棄されることを確認文で示す。アカウント画面の取りやめられないログアウトは、手元のデータを消さないので、止めて保存するだけにする。
- **L4**: ホームの「データ取得」の振り分けと入力の組み立てを `utils/homeDownload.ts` に切り出してテストした。

### 方針との差（2026-11-22 承認）

次の3点は方針の文言と実装が違っていたが、実装どおりとすることをユーザーが承認した。

| 項目 | 決定 |
|---|---|
| M8・L1 の PRIVATE | 管理者が他人の記録を変更・削除できるのは PUBLIC のレイヤだけ。PRIVATE は管理者も変えられない（墓標がメンバーに届かないため）。PRIVATE の整理は設定モード・クラウドデータ管理で行う |
| L1 のテンプレートの編集 | 一般メンバーもテンプレートの記録を編集でき、自分の記録として持ち替える（従来どおり）。テンプレートの削除は管理者だけ |
| L11 の単位 | レイヤ単位（自分の doc が丸ごと消えたときだけ確認する） |
